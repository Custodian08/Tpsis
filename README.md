# Система RFM-анализа клиентской базы

Система для анализа клиентской базы на основе RFM-анализа с интерактивной визуализацией результатов.

## Технологический стек

### Backend
- **Язык:** TypeScript 5.0+
- **Среда:** Node.js 20+
- **Фреймворк:** NestJS 10.0+
- **База данных:** PostgreSQL 16+
- **ORM:** TypeORM 0.3+
- **Аутентификация:** JWT + passport.js + bcrypt

### Frontend
- **Язык:** TypeScript 5.0+
- **Фреймворк:** React 18+
- **Сборщик:** Vite 5.0+
- **UI-библиотека:** Material-UI 5+
- **Визуализация:** Recharts
- **HTTP-клиент:** Axios
- **Управление состоянием:** Zustand

### Интеллектуальный компонент
- **Среда:** Node.js 20+
- **Реализация:** отдельный экспертный микросервис на встроенном HTTP-модуле Node.js, без внешних библиотек
- **Интеграция:** REST/JSON через серверный шлюз; микросервис получает только агрегаты сегментов

## Требования к системе

- Node.js 20+ 
- PostgreSQL 16+
- npm 10+ или yarn 1.22+ или pnpm 8+
- Windows 8+

## Установка и запуск

### 1. Клонирование репозитория

```bash
git clone https://github.com/Custodian08/Tpsis.git
cd "ТПИСИ курсовой проект"
```

### 2. Установка PostgreSQL

Установите PostgreSQL 16+ и создайте базу данных:

```sql
CREATE DATABASE rfm_analysis;
```

Для новой базы выполните `backend/database/init.sql`, затем SQL-миграции `001`, `002`, `003` из `backend/database/migrations` по порядку. Для уже работающей базы применяйте только ещё не выполненные миграции; `003_reliability_constraints.sql` проверяет исторические данные до изменения схемы. Миграции выполняются вручную в pgAdmin, не при старте backend.

**Ограничение текущей схемы:** анализы хранятся отдельно по пользователям, но клиенты и транзакции пока общие для всех учётных записей. Не загружайте в одну установку данные разных организаций до появления владельца/набора данных и миграции существующей базы.

### 3. Настройка Backend

Перейдите в директорию backend:

```bash
cd backend
```

Установите зависимости:

```bash
npm install
```

Скопируйте `backend/.env.example` в `backend/.env` и заполните значения:

```env
# Сервер
PORT=3000
NODE_ENV=development

# База данных PostgreSQL
DB_HOST=localhost
DB_PORT=5432
DB_USERNAME=postgres
DB_PASSWORD=your_password
DB_DATABASE=rfm_analysis

# JWT
JWT_SECRET=replace-with-a-random-secret-at-least-32-characters
JWT_EXPIRES_IN=15m

# Frontend
FRONTEND_URL=http://localhost:5173

# Интеллектуальный микросервис
AI_SERVICE_URL=http://127.0.0.1:8001
```

Для `JWT_SECRET` задайте случайное значение длиной не менее 32 символов, например сгенерируйте его локально командой `node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"`. Не используйте приведённую выше строку как секрет и не публикуйте содержимое `.env`.

Файл `backend/.env` содержит локальные пароли и секреты и исключён из Git. Регистрация принимает пароль от 8 символов; пароль хранится в PostgreSQL только в виде bcrypt-хеша. После входа сервер устанавливает JWT в cookie `HttpOnly`/`SameSite=Strict`; JavaScript приложения не получает токен и не хранит его в `localStorage`. Срок действия access-токена по умолчанию — 15 минут; выход очищает cookie в браузере. После обновления до этой версии нужно войти заново, так как старые токены из `localStorage` удаляются и больше не принимаются.

Для размещения вне локальной разработки настройте HTTPS на reverse proxy, задайте `NODE_ENV=production` и укажите точный HTTPS-адрес frontend в `FRONTEND_URL`. Backend помечает production-cookie как `Secure` и добавляет HSTS, поэтому без HTTPS вход работать не должен. Лимиты запросов входа, регистрации и импорта сейчас хранятся в памяти процесса; для нескольких экземпляров сервера их следует перенести в общий Redis или аналогичное хранилище. За reverse proxy дополнительно задайте Express `trust proxy` только для доверенного адреса/числа proxy, чтобы лимиты учитывали реальный адрес клиента и не доверяли подставленному заголовку.

Запустите backend сервер:

```bash
npm run start:dev
```

Сервер будет доступен по адресу: http://localhost:3000
Проверка доступности API и PostgreSQL: `GET http://localhost:3000/api/health` (статус 200 при готовности, 503 если БД недоступна).

### 4. Запуск интеллектуального микросервиса

Откройте отдельный терминал в корне проекта:

```bash
cd ai-service
npm start
```

Сервис интерпретации будет доступен backend по адресу `http://127.0.0.1:8001`. Серверная часть выступает AI Gateway: передаёт агрегаты по REST/JSON, ограничивает ожидание ответа и сохраняет RFM-результат, даже если интеллектуальный сервис недоступен. Экспертные правила готовят наблюдения и рекомендации, не меняют рассчитанные RFM-показатели и не получают персональные данные клиентов.

Для размещения на отдельном физическом узле запустите сервис с `HOST=0.0.0.0`, настройте `AI_SERVICE_URL` на backend и разрешите сетевой доступ только от него; для передачи между узлами настройте HTTPS.

### 5. Настройка Frontend

Откройте новый терминал и перейдите в директорию frontend:

```bash
cd frontend
```

Установите зависимости:

```bash
npm install
```

Запустите frontend сервер:

```bash
npm run dev
```

Фронтенд будет доступен по адресу: http://localhost:5173

## API документация

После запуска backend сервера, API доступно по адресу: http://localhost:3000/api

### Основные эндпоинты

#### Аутентификация
- `POST /api/auth/register` - Регистрация
- `POST /api/auth/login` - Вход
- `POST /api/auth/logout` - Выход и очистка auth-cookie
- `GET /api/auth/profile` - Профиль пользователя

Frontend автоматически отправляет HttpOnly-cookie авторизации на защищённые API-маршруты.

#### Данные
- `POST /api/data/import/csv` - Импорт CSV
- `POST /api/data/import/excel` - Импорт Excel
- `GET /api/data/clients?page=1&pageSize=25&search=` - Страница клиентов с поиском
- `GET /api/data/transactions?page=1&pageSize=25&clientId=&dateFrom=&dateTo=&search=` - Страница транзакций с фильтрами
- `GET /api/data/stats` - Статистика
- `GET /api/health` - Готовность API и PostgreSQL (без авторизации)

Списки данных возвращают `{ items, page, pageSize, total, totalPages }`; размер страницы ограничен 100 записями. Ошибки содержат `statusCode`, безопасное `message`, `requestId`, `timestamp` и `path`. Сведения SQL и тела запросов в журнал не записываются.

#### RFM-анализ
- `POST /api/rfm/analyze` - Выполнить анализ
- `GET /api/rfm/results/:configId` - Результаты анализа
- `GET /api/rfm/segments` - Список сегментов

#### Сегменты
- `GET /api/segments` - Все сегменты
- `GET /api/segments/stats` - Статистика сегментов
- `GET /api/segments/:id` - Детали сегмента

## Формат данных для импорта

Файл должен содержать следующие столбцы:

| Поле | Описание | Обязательно |
|------|----------|------------|
| client_id | Уникальный идентификатор клиента | Да |
| full_name | Полное имя клиента | Нет |
| email | Email клиента | Нет |
| phone | Телефон клиента | Нет |
| client_type | Тип клиента | Нет |
| transaction_date | Дата транзакции | Да |
| amount | Сумма покупки | Да |
| items_count | Количество товаров | Нет |
| payment_method | Способ оплаты | Нет |
