# Инициализация и обновление PostgreSQL

## Новая база данных

1. Создайте пустую базу `rfm_analysis` в pgAdmin или PostgreSQL.
2. Откройте базу в Query Tool и выполните `init.sql`, затем миграции `migrations/001_add_ai_interpretation.sql`, `002_store_rfm_calculation_rules.sql` и `003_reliability_constraints.sql`.
3. Из каталога `backend` запустите `npm run db:migrate-ownership`. Скрипт сделает резервную копию и применит миграцию 004.
4. Для демонстрационных данных при необходимости выполните `seed_data.sql` после миграций. Тестовые учётные данные из seed-файла предназначены только для локальной демонстрации.

## Существующая база

Не запускайте `init.sql` поверх уже работающей базы. Сначала создайте и проверьте резервную копию, затем применяйте только ещё не выполненные миграции в указанном выше порядке. Миграции запускаются вручную через pgAdmin Query Tool или PostgreSQL `psql`, не при старте API.

Для автоматической копии и миграции 004 из каталога `backend` запустите `npm run db:migrate-ownership`. Команда сохранит custom-format архив в игнорируемой Git-папке `.local-backups`, применит миграцию, затем проверит владельцев клиентов и исторических оценок. Только создать копию можно командой `npm run db:backup`; проверить восстановление можно командой `npm run db:verify-backup -- <файл.dump> <users> <clients> <transactions> <scores>`. Одна рабочая копия уже проверена восстановлением во временную БД.

`003_reliability_constraints.sql` проверяет старые данные перед созданием ограничений. Если обнаружены недопустимые значения или повторные оценки, миграция прекращает работу; исправьте данные и повторите её.

## Миграция владения клиентскими данными

Миграция `004_client_data_ownership.sql` добавляет владельца к клиентам и заменяет уникальность внешнего ID на уникальность внутри аккаунта.

- Если в базе ровно один пользователь, существующие клиенты автоматически назначаются ему.
- Если пользователей несколько, прежний общий набор клиентов и транзакций копируется каждому существующему аккаунту. Исторические RFM-оценки переназначаются на клиентские копии соответствующего владельца, поэтому история анализов сохраняется.
- Новые импорты создают отдельные записи для владельца; одинаковые внешние ID разрешены в разных аккаунтах.
- При нескольких аккаунтах объём старых клиентских данных после миграции увеличится пропорционально числу пользователей. Перед применением сделайте резервную копию и проверьте свободное место.

Если в базе есть клиенты, созданные до появления первого аккаунта, миграция не может определить их владельца. Проверьте их и повторно примените миграцию 004 после создания аккаунта:

```sql
SELECT id, client_external_id, full_name
FROM clients
WHERE owner_user_id IS NULL
ORDER BY id;
```

Такие записи будут назначены/скопированы автоматически при повторном запуске миграции. Клиент и его транзакции связаны через `client_id`, поэтому транзакциям отдельное поле владельца не требуется.

## Seed-данные и схема

`seed_data.sql` добавляет локальные демонстрационные аккаунты, клиентов и транзакции. Новые демонстрационные клиенты принадлежат `user@example.com`. Не используйте демонстрационные пароли в рабочем окружении.

Основные таблицы:

- `users` — аккаунты пользователей.
- `clients` — клиентские записи и `owner_user_id`.
- `transactions` — покупки, принадлежащие владельцу через клиента.
- `analysis_configs`, `rfm_scores` — параметры и результаты анализов.
- `segments`, `segment_rfm_scores` — справочник сегментов и связь оценок с сегментами.

Автоматизированные миграционные проверки создают отдельную временную базу; см. [план и протокол тестирования](../../Документация/TEST_PLAN_AND_REPORT.md).
