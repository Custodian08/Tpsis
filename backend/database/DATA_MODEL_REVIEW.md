# Предварительная проверка модели данных

Проверено по `init.sql` и TypeORM entity на 2026-09-27. Это статический анализ
структуры; состояние и дубликаты в локальной PostgreSQL нужно проверить отдельно.

| Таблица | Основные зависимости | Оценка |
| --- | --- | --- |
| `users` | `id → email, password, full_name, role, is_active`; email уникален | Атрибуты относятся к одному пользователю; структура соответствует 3НФ. |
| `clients` | `id → client_external_id, full_name, email, phone, client_type`; внешний ID уникален | Атрибуты клиента не дублируют транзакции. Уникальность сейчас глобальная, владельца/набора данных нет. |
| `transactions` | `id → client_id, transaction_date, amount, items_count, payment_method` | Данные покупки отделены от клиента; `client_id` — внешний ключ. Соответствует 3НФ при текущем составе. |
| `analysis_configs` | `id → user_id, параметры периода и расчёта` | Параметры запуска отделены от пользователя и результатов. Пользователь задан внешним ключом. |
| `rfm_scores` | `id → analysis_config_id, client_id, метрики и оценки`; одна оценка клиента на анализ | Миграция 003 закрепляет уникальность пары анализа и клиента. `rfm_segment` повторяет код, вычисляемый из трёх оценок; он сохранён для выборок, поэтому это намеренная денормализация. |
| `segments` | `rfm_pattern → название и описание` | Справочник шаблонов. `client_count` и `avg_monetary` — производные поля, приложение строит эти итоги из оценок; поля справочника исторически лишние и не являются источником аналитики. Удалять их следует отдельной миграцией после проверки внешних потребителей. |
| `segment_rfm_scores` | `(rfm_score_id, segment_id)` — первичный ключ пары | Нормальная связующая таблица для отношения многие-ко-многим. |

Ключевые отношения закреплены первичными/внешними ключами в `init.sql`; миграция
003 добавляет недостающую уникальность и индексы по основным выборкам. Перед
применением проверьте её preflight-проверки на копии рабочей базы.

## Ограничение области доступа

RFM-запуски привязаны к пользователю, но записи `clients` и `transactions`
общие. Поэтому текущая схема не обеспечивает изоляцию импортированных наборов
данных между зарегистрированными пользователями. Для многопользовательского
развёртывания нужна отдельная сущность набора данных/владельца, составная
уникальность внешнего ID в рамках набора и миграция старых данных с явно
подтверждённым владельцем.
