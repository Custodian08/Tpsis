# План и протокол тестирования

**Проект:** программное средство анализа клиентской базы на основе RFM-анализа с интерактивной визуализацией.  
**Дата автоматизированной проверки:** 01.11.2026.  
**Назначение:** зафиксировать проверенные сценарии и ограничения фактически выполненного тестирования. Документ не заменяет ручную приёмку и должен обновляться после следующих изменений.

## 1. Цели и область проверки

Проверяется корректность RFM-правил и серверной валидации, безопасная обработка импорта, разделение клиентских данных между аккаунтами, API основного аналитического сценария, применение миграций на отдельной тестовой базе, а также сборка и статические проверки backend/frontend.

Проверки выполняются на синтетических данных. Реальная пользовательская база в тестах миграции и E2E не используется и не изменяется.

## 2. Среда и запуск

Backend-тесты выполняются из каталога `backend`:

```text
npm run build
npm test -- --runInBand
npm run test:migrations
npm run test:e2e
```

Frontend-проверки выполняются из каталога `frontend`:

```text
npm run build
npm run lint
```

`test:migrations` и `test:e2e` создают отдельные временные PostgreSQL-базы с именами `rfm_qa_*` и `rfm_e2e_*`, применяют SQL-схему/миграции и удаляют базу после завершения. Для этих команд требуется доступ к PostgreSQL и параметры подключения из локального окружения. Не записывайте секреты подключения в этот отчёт или Git.

## 3. План и критерии

| Направление | Проверяемое поведение | Критерий прохождения |
|---|---|---|
| Unit-тесты backend | RFM-правила, DTO, импорт, auth и вспомогательные сервисы | Все тестовые наборы завершились без ошибок |
| Миграции PostgreSQL | Инициализация и последовательное применение миграций; повторный запуск проверяемого ограничения; владение старым набором | SQL завершается успешно на временной базе, некорректные данные отклоняются, неоднозначный владелец не назначается автоматически |
| Авторизация и API | Health, закрытые маршруты, регистрация, cookie, история, анализ, logout | Ожидаемые HTTP-коды и данные; чужой анализ недоступен |
| Импорт CSV/Excel | Предпросмотр без записи, подтверждённый импорт, валидация и ограничения | Предпросмотр не меняет БД; корректный файл записывается после подтверждения; некорректный отклоняется |
| Изоляция аккаунтов | Два аккаунта импортируют одинаковый внешний ID | Оба набора независимы; статистика, поиск и анализ не раскрывают данные другого аккаунта |
| Frontend | TypeScript, production-сборка, ESLint | Все команды завершаются успешно |
| Ручная приёмка | Полный сценарий в браузере, адаптивность, доступность и экспорт | Отдельный ручной протокол с окружением и результатами |

## 4. Фактические результаты

### 4.1 Backend

- `npm run build` — пройдено.
- `npm test -- --runInBand` — пройдено: 6 наборов, 21 тест.
- `npm run test:migrations` — пройдено на временной базе: `init.sql`, миграции 001–003 и миграция 004; проверены назначение старых данных единственному пользователю, копирование старых клиентов/транзакций для нескольких аккаунтов, сохранение привязки исторических оценок и идемпотентность повторного запуска.
- `npm run test:e2e` — пройдено: 51 HTTP-проверка на временной базе.
- Миграция 004 применена и повторно проверена на рабочей `rfm_analysis` после создания резервной копии. До миграции было 3 аккаунта, 40 клиентов, 66 транзакций и 200 оценок; после — 120 клиентов (40 на аккаунт), 198 транзакций (66 на аккаунт), 200 оценок. Проверки показали 0 клиентов без владельца и 0 оценок, привязанных к чужому владельцу. Повторный запуск миграции не создал новых строк.
- Резервные копии до и после миграции созданы в `backend/.local-backups/` в формате PostgreSQL custom archive. Обе восстановлены во временные БД с совпадением контрольных количеств (до: 3/40/66/200; после: 3/120/198/200), временные БД удалены.

### 4.2 Покрытые HTTP-сценарии

- Готовность API/БД и запрет доступа к закрытой статистике без авторизации.
- Регистрация, выдача безопасного профиля, аутентификация cookie и logout.
- Предпросмотр CSV показывает число клиентов/транзакций и строки примера; статистика подтверждает, что до подтверждения импорта записи не появились.
- Подтверждённый CSV-импорт, пагинация/поиск клиентов и отклонение несуществующей даты.
- Запуск RFM-анализа и сохранение истории.
- Два независимых аккаунта импортируют одинаковый внешний ID: каждый видит только свой профиль, статистику, клиентский и транзакционный поиск, собственные RFM-результаты и карточки клиентов; история содержит только анализы владельца, чужой анализ недоступен.
- Предпросмотр и подтверждённый импорт Excel через HTTP; записи относятся только к аккаунту-импортёру.
- Очистка cookie при выходе и запрет закрытого запроса без cookie.

### 4.3 Frontend

- `npm run build` — пройдено: TypeScript-проверка и production-сборка успешны; страницы загружаются динамически.
- `npm run lint` — пройдено.
- Начальный JS-чанк после разделения страниц — около 376 КБ; отдельный чанк диаграмм — около 372 КБ. Предупреждения о чанках свыше 500 КБ больше нет.
- После миграции локально запущены frontend, backend и AI-service; проверки `/login`, `/api/health` и `/health` вернули HTTP 200. Визуальная ручная приёмка в браузере ещё не выполнялась.

## 5. Непроверенные сценарии и ограничения

- Полный путь пользователя в браузере вручную, включая визуальную проверку новой страницы импорта.
- Клавиатурная навигация, экранный диктор, контрастность и узкие экраны.
- Открытие экспортированных CSV/JSON в Excel и LibreOffice на разных системах.
- Регулярное автоматическое расписание резервных копий, TLS и запуск на чистой машине. Восстановление проверено для резервных копий до и после миграции.
- Качество рекомендаций экспертного AI-сервиса на размеченных контрольных примерах и согласование его статуса с руководителем.
- Резервные копии рабочей базы хранятся локально в игнорируемом Git-каталоге; копии до и после миграции успешно восстановлены во временные базы.
- Поведение при сбое/откате импорта на реальном сервере, больших файлах у граничного размера и конкурентных импортах требует отдельной нагрузки/интеграционной проверки.

## 6. Вывод

Автоматизированные проверки подтверждают работу основных API-сценариев, RFM-анализа, предварительной проверки CSV/Excel и разграничения новых клиентских наборов между аккаунтами на изолированной тестовой базе. Для сдачи курсового проекта нужно дополнить протокол ручной приёмкой, проверить рабочую миграцию после резервного копирования и документировать оставшиеся ограничения.
