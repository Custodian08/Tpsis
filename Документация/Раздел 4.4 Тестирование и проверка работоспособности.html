4.4 Тестирование и проверка работоспособности программного средства

В разделе рассматриваются подход к проверке веб-приложения анализа клиентской базы, тестовые сценарии серверной и клиентской частей, отдельная проверка интеллектуального компонента и правила оценки результатов испытаний. Основное внимание уделено корректности расчёта RFM, сохранности данных, обработке ошибок и доступности результатов при отказе сервиса интерпретации.

Статус фактических результатов. В репозитории обнаружены автоматические тесты правил RFM, backend-модулей и экспертного микросервиса, а также сценарии API и миграций. Численные итоги их последнего запуска здесь не заявляются, поскольку запуск в рамках подготовки этого раздела не выполнялся. В таблицах результата предусмотрено заполнение по фактическому прогону.

4.4.1 Стратегия и план тестирования

Цель тестирования — проверить соответствие реализованных функций требованиям, выявить ошибки обработки данных и подтвердить, что отказ вспомогательного интеллектуального сервиса не нарушает основной RFM-анализ. Проверки разделяются по уровням: модульные тесты отдельных функций, интеграционные проверки взаимодействия компонентов и сценарные проверки API и пользовательских операций.

Тестирование проводится в изолированной среде разработки с отдельной тестовой базой PostgreSQL и синтетическими данными. В тестовых наборах используются фиксированные даты, суммы и идентификаторы, чтобы ожидаемые результаты можно было воспроизвести. Персональные данные реальных клиентов для тестирования не требуются.

Отдельный сценарий API предназначен для сквозной проверки взаимодействия с сервером; скрипт проверки миграций проверяет применение ограничений к тестовой базе.

Пример модульной проверки

it('сохраняет равные значения в одной оценочной группе', () => {
  expect(calculateRankScores([1, 1, 2, 3], 5, false))
    .toEqual([1, 1, 4, 5]);
});

Данный тест проверяет важное правило оценивания: совпадающие значения не должны получать различные оценки только ради выравнивания числа клиентов в квантилях.

4.4.3 Тестирование и валидация интеллектуального компонента

Интеллектуальный компонент является экспертным сервисом с фиксированными правилами. Поэтому его проверка включает валидацию входного контракта, корректность интерпретационных правил, обработку граничных значений и отказоустойчивость интеграции с backend. Качество оценивается не метриками обучения классификатора, а соответствием результата заданным правилам и полнотой обработки допустимых запросов.

В backend проверяется формат ответа микросервиса: сводка должна быть строкой, наблюдения и рекомендации — массивами строк. Для сетевого вызова установлен тайм-аут четыре секунды, длина полей ответа ограничивается перед сохранением. При неуспешном статусе, нарушении контракта или сетевой ошибке backend формирует результат со статусом недоступности и продолжает возвращать основной RFM-расчёт.

4.4.4 Результаты тестирования и оценка надежности

Результаты тестирования фиксируются по фактическому запуску автоматических наборов и пользовательских сценариев. Для каждого уровня указываются количество выполненных проверок, успешные случаи, ошибки и процент успешного выполнения.

Процент успешного выполнения рассчитывается по формуле: P = Nусп / Nвсего × 100 %, где Nусп — число успешно завершённых проверок, Nвсего — общее число выполненных проверок. Неисполненные сценарии не следует учитывать как пройденные.

При обнаружении дефекта в отчёте указываются тестовый уровень, условие воспроизведения, затронутый компонент, влияние на результат, внесённое исправление и результат повторной проверки. После исправления соответствующие тесты выполняются повторно, чтобы подтвердить устранение ошибки и отсутствие регрессии.

Оценка надежности

Надёжность программного средства в рамках проекта оценивается по контролируемой обработке ошибок и сохранению целостности результатов: валидация запросов предотвращает обработку некорректных параметров; транзакционное сохранение связывает конфигурацию запуска и оценки; ограничения базы данных защищают ключевые инварианты; сбой интеллектуального сервиса не отменяет RFM-результаты. Количественный коэффициент без измерений времени отказов и восстановления не рассчитывается.

Заключение. Программное средство считается готовым к демонстрации после успешного прохождения запланированных модульных, интеграционных и пользовательских проверок, заполнения сводной таблицы фактическими результатами и повторной проверки всех исправленных дефектов. Итоговая оценка качества должна опираться на приложенные протоколы запуска, а не на предварительные предположения.
