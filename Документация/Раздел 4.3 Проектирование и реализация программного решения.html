4.3 Проектирование и реализация программного решения

В разделе описаны архитектура разработанного программного средства RFM-анализа клиентской базы, его информационная база, интеллектуальный компонент, пользовательские и программные интерфейсы, алгоритмы и меры защиты.

4.3.1 Разработка архитектуры и определение ее компонентов

Разрабатываемое программное средство предназначено для загрузки и анализа истории покупок клиентов, расчёта показателей Recency, Frequency и Monetary, сегментации клиентской базы и представления результатов в интерактивной форме. Архитектура разделяет пользовательский интерфейс, серверную бизнес-логику, реляционное хранилище и интеллектуальный компонент.

КомпонентРеализация и назначение
Клиентское приложениеОдностраничное веб-приложение React. Предоставляет регистрацию и вход, загрузку данных, запуск анализа, просмотр истории и результатов, сегментов, визуализаций и экспорт.
Серверное приложениеBackend на NestJS. Проверяет запросы и права доступа, обрабатывает данные, выполняет RFM-расчёты, сохраняет результаты, предоставляет API и вызывает интеллектуальный микросервис.
База данныхPostgreSQL хранит учётные записи, клиентов, транзакции, параметры анализов, рассчитанные оценки и сегменты.
Интеллектуальный микросервисОтдельный Node.js HTTP-сервис. Получает только агрегаты сегментов и возвращает сводку, наблюдения и рекомендации по фиксированным правилам.

Клиентская часть отвечает за представление данных и взаимодействие с пользователем. Проверка входных данных и все расчёты, влияющие на числовой результат, выполняются на сервере. Вызов микросервиса является дополнительным этапом после расчёта: при его ошибке или превышении времени ожидания сформированные оценки и сегменты сохраняются, а пользователю возвращается статус недоступности интерпретации.

В текущей схеме пользователи имеют собственные анализы, однако записи клиентов и транзакций общие для учётных записей. Поэтому система не должна использоваться для совместного размещения данных нескольких независимых организаций без доработки модели владения клиентскими наборами.

4.3.2 Обоснование и выбор технологического стека для реализации

Технологический стек выбирался с учётом требований к веб-интерфейсу, обработке клиентских данных, выполнению повторяемых аналитических расчётов и интеграции с отдельным интеллектуальным компонентом. Для сравнения рассматривались альтернативы, которые позволяют реализовать клиент-серверное приложение с реляционным хранилищем.

Выбор архитектурного подхода

В качестве основы выбрана клиент-серверная архитектура с модульным серверным приложением и отдельно размещённым сервисом интеллектуальной интерпретации. Браузер отвечает за отображение и ввод данных, сервер — за правила доступа, проверку и обработку наборов данных, расчёт RFM и работу с хранилищем. Внешний по отношению к основному серверу микросервис выполняет только интерпретацию агрегатов. Такое разделение сохраняет простоту разработки основной системы и позволяет изолировать компонент, отказ которого не должен нарушать расчёт.

Полный переход к микросервисной архитектуре для всех функций не выбран: на текущем объёме проекта он добавил бы отдельное развёртывание, сетевые взаимодействия и сопровождение нескольких сервисов без необходимости независимо масштабировать каждый доменный модуль. Вместе с тем интеллектуальная интерпретация уже вынесена в отдельный сервис, поскольку это прямо соответствует заданной архитектуре и позволяет отделить недетерминированную по доступности интеграцию от детерминированной бизнес-логики.

Таким образом, основная часть реализована как модульное серверное приложение, а отдельный микросервис используется для ограниченной функции интерпретации. Этот компромисс обеспечивает понятное разделение компонентов без усложнения всей системы.

Выбор серверной платформы и фреймворка

Для серверной части сравнивались NestJS на платформе Node.js, ASP.NET Core и Spring Boot. Все три варианта подходят для создания REST API и работы с реляционными базами данных. Выбор оценивался по соответствию языку клиентской части, модульности, возможностям валидации и удобству реализации данного учебного проекта.

NestJS выбран потому, что серверная логика уже реализована на TypeScript, а интерфейс использует тот же язык. Это позволяет использовать схожие подходы к типизации данных и облегчает поддержку API-контрактов. Модульная структура NestJS соответствует разделению проекта на авторизацию, пользователей, импорт данных, RFM-анализ и сегменты. ASP.NET Core и Spring Boot обладают достаточными возможностями, однако в рамках данного проекта не дают преимущества, которое компенсировало бы необходимость введения дополнительного языка и отдельной технологической среды. Выбор не означает, что альтернативы хуже по производительности или надёжности; сравнение обусловлено требованиями и составом данного проекта.

PostgreSQL выбрана благодаря соответствию реляционной структуре данных и использованию внешних ключей для контроля ссылочной целостности. MySQL также могла бы обслуживать данную модель, поэтому выбор PostgreSQL не основывается на утверждении о принципиальном превосходстве в любых аналитических задачах. MongoDB менее удобна для основной модели, где важны связи и согласованное сохранение данных. Доступ к базе данных реализован через TypeORM, а изменение схемы выполняется миграциями.

Итоговый состав стека

В результате сравнения выбран следующий набор технологий: React и TypeScript для клиентского приложения; Vite для сборки; Material UI для базовых компонентов интерфейса; Recharts для диаграмм; Axios для HTTP-взаимодействия; Zustand для состояния клиентского приложения; Node.js, TypeScript и NestJS для серверной части; TypeORM для доступа к данным; PostgreSQL для реляционного хранения; Node.js HTTP-сервис для экспертной интерпретации; JWT, Passport и bcrypt для аутентификации и защиты учётных данных.

Выбор обусловлен не абстрактным превосходством одной платформы, а соответствием текущим требованиям и реализованному коду: единый язык TypeScript для клиента и backend, модульное разделение серверной логики, реляционная модель данных и возможность изолировать интеллектуальную обработку. Рассмотренные альтернативы являются технически применимыми, однако их использование потребовало бы смены уже реализованной платформы без функциональной необходимости.

4.3.3 Разработка информационной базы и структуры данных

Проектирование информационной базы выполнялось с учётом предметной области анализа клиентской базы методом RFM и выбранной архитектуры программного средства. Модель данных должна обеспечивать хранение сведений о пользователях, клиентах и транзакциях, сохранение параметров каждого анализа, фиксацию полученных оценок и доступ к агрегированным характеристикам сегментов.

На концептуальном этапе были выделены основные сущности предметной области: пользователь, клиент, транзакция, конфигурация анализа, RFM-оценка и сегмент. Интеллектуальная интерпретация хранится как часть конфигурации соответствующего запуска, поскольку она описывает сводные результаты этого анализа.

На логическом этапе сущности представлены реляционными таблицами. Для каждой таблицы определён первичный ключ; связи между таблицами реализованы внешними ключами. Один клиент связан с несколькими транзакциями и результатами анализа; одна конфигурация анализа включает множество оценок; результаты анализа и справочник сегментов связаны отношением «многие-ко-многим» через отдельную связующую таблицу.

На физическом этапе модель реализована в PostgreSQL. Сущности приложения описаны средствами TypeORM, начальная структура задаётся SQL-скриптом, а последующие изменения — миграциями. Для показателей используются целочисленные и десятичные типы, для дат периода — тип DATE, для сохранённого ответа интеллектуального сервиса — JSONB. Внешние ключи и ограничения CHECK и UNIQUE контролируют ссылочную целостность, допустимые диапазоны и отсутствие повторной оценки одного клиента в рамках одного анализа.

Основные таблицы информационной базы и их атрибуты представлены ниже.

Таблица «users»

Таблица предназначена для хранения учётных записей пользователей приложения и содержит:

  • id — первичный ключ, идентификатор пользователя;
  • email — адрес электронной почты, уникальный и обязательный;
  • password — хеш пароля;
  • full_name — имя пользователя;
  • role — роль пользователя;
  • is_active — признак активности учётной записи;
  • created_at, updated_at — даты создания и последнего изменения записи.

Таблица «clients»

Таблица хранит сведения о клиентах, для которых загружается история покупок:

  • id — первичный ключ;
  • client_external_id — внешний идентификатор клиента, обязательный и уникальный;
  • full_name — имя клиента;
  • email, phone — контактные данные;
  • client_type — тип клиента;
  • created_at, updated_at — даты создания и обновления записи.

Таблица «transactions»

Таблица предназначена для хранения покупок и иных загруженных транзакций:

  • id — первичный ключ;
  • client_id — внешний ключ на клиента;
  • transaction_date — дата транзакции;
  • amount — денежная сумма с точностью до двух знаков;
  • items_count — число товаров, по умолчанию равное единице;
  • payment_method — способ оплаты;
  • created_at — дата добавления записи.

Внешний ключ транзакции ссылается на таблицу клиентов. Для количества товаров установлено ограничение положительного значения. В расчёте Frequency используется количество строк транзакций, а не значение items_count.

Таблица «analysis_configs»

Таблица хранит параметры и метаданные отдельного запуска RFM-анализа:

  • id — первичный ключ;
  • user_id — идентификатор пользователя, создавшего анализ;
  • config_name — название анализа;
  • analysis_period — продолжительность периода анализа в календарных днях;
  • period_start, period_end — начало и конец периода;
  • reference_date — дата, относительно которой рассчитывается Recency;
  • quartiles_count — количество уровней квантильной оценки, от 3 до 10;
  • scoring_method_version — версия алгоритма оценивания;
  • r_weights, f_weights, m_weights — поля весов соответствующих оценок, если они заданы;
  • ai_interpretation — JSON-объект со статусом, сводкой, наблюдениями и рекомендациями микросервиса;
  • created_at — дата создания анализа.

Для новых запусков используется версия правил midpoint-rank-v1. Параметры периода, дата отсчёта и версия алгоритма сохраняются, чтобы результат можно было интерпретировать с учётом условий его получения.

Таблица «rfm_scores»

Таблица содержит рассчитанные показатели и оценки клиента в рамках конкретного запуска:

  • id — первичный ключ;
  • client_id — внешний ключ на клиента;
  • analysis_config_id — внешний ключ на конфигурацию анализа;
  • recency_days — значение Recency в календарных днях;
  • frequency_count — число транзакций клиента в периоде;
  • monetary_value — сумма транзакций;
  • r_score, f_score, m_score — оценки по трём компонентам;
  • rfm_segment — сформированный RFM-код;
  • analysis_date — время фиксации результата.

Сочетание analysis_config_id и client_id уникально: один клиент получает не более одной оценки в рамках одного анализа. Ограничения базы проверяют, что Recency неотрицателен, Frequency положителен, а оценки находятся в поддерживаемом диапазоне от 1 до 10.

Таблица «segments»

Таблица содержит справочные сведения о сегментах:

  • id — первичный ключ;
  • segment_name — уникальное название сегмента;
  • rfm_pattern — уникальный RFM-код или шаблон;
  • description — текстовое описание;
  • client_count — количество клиентов в сегменте;
  • avg_monetary — среднее значение Monetary;
  • created_at — дата создания записи.

Таблица «segment_rfm_scores»

Связующая таблица реализует связь между оценками и сегментами. Она содержит rfm_score_id и segment_id, являющиеся внешними ключами на соответствующие таблицы. Составной первичный ключ предотвращает повторное добавление одной и той же пары. При удалении связанной оценки или сегмента зависимые записи связи удаляются каскадно.

Разработанная информационная модель отражает основные объекты процесса RFM-анализа: пользователей, клиентов, историю покупок, параметры запуска, оценки и сегменты. Сохранение конфигурации вместе с рассчитанными значениями обеспечивает связь результата с периодом и версией алгоритма. Внешние ключи, уникальные ограничения, проверки диапазонов и индексы поддерживают целостность и ускоряют типовые запросы. Схема реализована в PostgreSQL с использованием TypeORM и последовательных SQL-миграций.

Особенность текущей реализации: анализы принадлежат отдельным пользователям, однако таблицы clients и transactions не содержат владельца набора данных. Следовательно, сведения о клиентах и транзакциях общие в пределах одной базы. Также отдельные сущности для статусов отмены и возврата не предусмотрены.

4.3.4 Проектирование и разработка интеллектуального компонента

Интеллектуальный компонент представляет собой экспертную систему на основе правил, реализованную отдельным HTTP-микросервисом. Его задача — сформировать текстовое пояснение уже рассчитанных результатов. Он не выполняет RFM-расчёт, не обучается на исторических данных и не изменяет исходные оценки.

Backend отправляет JSON-запрос, содержащий общее количество клиентов, число квантилей и список агрегатов сегментов: название, RFM-код, число клиентов и среднее значение Monetary. Персональные данные и строки отдельных транзакций в запрос не включаются. Сервис проверяет структуру, допустимость кодов и согласованность агрегатов, затем применяет правила выделения крупнейших, денежно значимых, условно лояльных и рискованных групп.

Результат содержит поля summary, insights и recommendations. Backend проверяет типы полей, ограничивает ожидание четырьмя секундами и ограничивает длину возвращаемого текста. При сетевой ошибке, некорректном ответе или тайм-ауте фиксируется статус недоступности, а RFM-результаты остаются доступными.

Названия «риск» и «лояльность» в интерпретации обозначают эвристические группы по заданным оценкам RFM. Они не являются подтверждённым прогнозом оттока или доказательством будущей выручки. Денежный вклад оценивается по агрегатам текущего анализа.

4.3.5 Проектирование и разработка интерфейса пользователя и схемы взаимодействия

Пользователь работает с системой через веб-интерфейс. Основные страницы обеспечивают регистрацию и вход, загрузку данных, настройку и запуск RFM-анализа, просмотр аналитической панели, сегментов, результатов и истории запусков. Доступные операции зависят от состояния авторизации.

  1. Пользователь регистрируется или входит в систему.
  2. Загружает файл данных о клиентах и транзакциях; сервер проверяет структуру и значения.
  3. Задаёт границы периода и число квантилей и запускает расчёт.
  4. Сервер вычисляет метрики и сегменты, сохраняет параметры и результаты.
  5. Сервер запрашивает интерпретацию у микросервиса и сохраняет её статус.
  6. Интерфейс показывает числовые показатели, таблицы, диаграммы и доступный текст интерпретации.

Фильтрация и переход к деталям позволяют исследовать результаты на уровне клиентской базы, сегмента и клиента. Представление данных должно отличать успешно полученную интерпретацию от сообщения о временной недоступности сервиса; недоступность интерпретации не скрывает основные показатели.

Клиентское приложение взаимодействует с backend через REST API с JSON-форматом. Глобальный префикс серверных маршрутов — /api. Для запросов, требующих авторизации, браузер отправляет учётную cookie; сервер проверяет её и права доступа. Серверное приложение обращается к PostgreSQL через TypeORM.

4.3.7 Разработка и описание алгоритмов, реализующих бизнес-логику

В данном подразделе приведены основные алгоритмы работы программного средства. Для каждого алгоритма указаны цель, последовательность действий и результат выполнения. Фрагменты кода иллюстрируют ключевые операции серверной части.

Алгоритм аутентификации пользователя

Цель: проверить учётные данные пользователя и предоставить доступ к защищённым функциям приложения.

Предпосылки: пользователь зарегистрирован, учётная запись активна, сервер доступен.

Шаги:

  1. На странице входа пользователь вводит адрес электронной почты и пароль.
  2. Клиент отправляет данные на серверный маршрут POST /api/auth/login.
  3. Сервер проверяет запрос и применяет ограничение частоты попыток входа.
  4. Сервис аутентификации находит пользователя и сравнивает введённый пароль с сохранённым bcrypt-хешем.
  5. При успешной проверке формируется JWT. Сервер помещает его в cookie rfm_access_token с флагом HttpOnly и возвращает публичные сведения о пользователе.
  6. При последующих обращениях JWT guard проверяет cookie и передаёт идентификатор пользователя защищённому обработчику.
  7. При неверных данных сервер возвращает ошибку, которую клиент отображает пользователю; токен не выдаётся.

Результат: при успехе браузер получает защищённую cookie и доступ к маршрутам, требующим авторизации; при ошибке пользователь видит сообщение и может повторить попытку.

// AuthController: выдача токена в HttpOnly cookie
const result = await this.authService.login(loginDto);
response.cookie('rfm_access_token', result.accessToken, {
  path: '/', sameSite: 'strict',
  secure: process.env.NODE_ENV === 'production',
  httpOnly: true,
});
return { user: result.user };

Алгоритм импорта клиентских данных

Цель: загрузить транзакции из CSV или Excel и сохранить валидные сведения для последующего анализа.

Предпосылки: пользователь авторизован; файл содержит предусмотренные форматом поля; размер файла не превышает 10 Мбайт.

Шаги:

  1. Пользователь открывает страницу импорта, выбирает CSV- или Excel-файл и запускает загрузку.
  2. Клиент передаёт файл в multipart-запросе на POST /api/data/import/csv или POST /api/data/import/excel.
  3. Сервер проверяет авторизацию, число файлов и ограничение размера.
  4. Сервис импорта разбирает строки, проверяет обязательные значения и корректность типов, затем связывает транзакции с клиентами по внешнему идентификатору.
  5. Ошибочные строки или неподдерживаемая структура обрабатываются по правилам сервиса импорта; клиент получает итог операции и сведения об ошибках.
  6. После успешного импорта пользователь может перейти к запуску анализа.

Результат: принятые записи доступны серверному модулю RFM; при отсутствии файла или превышении ограничения запрос отклоняется с сообщением об ошибке.

// DataController: ограничение загрузки файла
FileInterceptor('file', {
  limits: { fileSize: 10 * 1024 * 1024, files: 1, fields: 0 },
})

Алгоритм проведения RFM-анализа

Цель: рассчитать метрики и оценки клиентов, сформировать сегменты и сохранить результат запуска.

Предпосылки: пользователь авторизован; даты заданы в формате ГГГГ-ММ-ДД; дата начала не позже даты окончания; в выбранном периоде имеются транзакции; число квантилей находится в диапазоне от 3 до 10.

Шаги:

  1. Пользователь задаёт период анализа и число квантилей и отправляет запрос POST /api/rfm/analyze.
  2. Сервер проверяет даты и вычисляет продолжительность периода с включением обеих граничных дат.
  3. Из базы выбираются транзакции, дата которых попадает в заданный период. Если найдено более 100 000 транзакций, сервер просит сузить период; если транзакций нет, анализ не запускается.
  4. Для каждого клиента рассчитываются Recency — календарные дни от последней покупки до даты окончания периода, Frequency — количество строк транзакций, Monetary — сумма денежных значений транзакций.
  5. Для каждого показателя вычисляется оценка от 1 до q по среднему рангу группы равных значений. Для Recency направление обратное; равные значения не разделяются.
  6. Из оценок формируется RFM-код, после чего создаются или обновляются сведения о встреченных шаблонах сегментов.
  7. Конфигурация анализа и оценки клиентов сохраняются в одной транзакции базы данных. Для каждого клиента и запуска допускается не более одной оценки.
  8. Сервер рассчитывает агрегаты сегментов и запрашивает для них интерпретацию у интеллектуального сервиса.
  9. Конфигурация дополняется результатом интерпретации или статусом её недоступности, затем клиенту возвращаются показатели, сегменты и сводные данные.

Результат: сохранённый запуск с параметрами и RFM-оценками, доступный для просмотра истории и аналитических экранов. Сбой интеллектуального сервиса не отменяет сохранённый числовой анализ.

// RfmService: выбор транзакций в периоде
const transactions = await this.transactionRepository.find({
  where: { transactionDate: Between(start, end) },
  relations: ['client'],
  take: MAX_ANALYSIS_TRANSACTIONS + 1,
});

if (transactions.length > MAX_ANALYSIS_TRANSACTIONS) {
  throw new BadRequestException('Уточните период анализа');
}
const clientMetrics = calculateClientMetrics(transactions, end);
const recencyScores = calculateRankScores(
  clientMetrics.map(metric => metric.recency), quartilesCount, true,
);

Алгоритм интеллектуальной интерпретации

Цель: сформировать понятное аналитическое пояснение по итогам сегментации, не изменяя расчётные показатели.

Предпосылки: сервер завершил RFM-расчёт и подготовил агрегаты сегментов; сервис доступен по настроенному адресу.

Шаги:

  1. Backend передаёт микросервису общее количество клиентов, число квантилей и по каждому сегменту название, RFM-код, количество клиентов и среднее значение Monetary.
  2. Сервис проверяет структуру запроса, допустимость RFM-кодов, диапазон квантилей и согласованность агрегатов.
  3. Экспертные правила определяют крупнейшие и денежно значимые сегменты, а также группы, соответствующие эвристическим критериям лояльности или риска.
  4. Микросервис формирует краткую сводку, список наблюдений и рекомендации и возвращает JSON-ответ.
  5. Backend ожидает ответ не более четырёх секунд, проверяет типы и длину полей и сохраняет интерпретацию с конфигурацией анализа.
  6. При сетевой ошибке, тайм-ауте или некорректном ответе фиксируется статус недоступности; основной результат RFM сохраняется.

Результат: интерпретация доступна как вспомогательное пояснение. Указанные сервисом «риск» и «лояльность» являются эвристическими характеристиками групп, а не прогнозом поведения клиентов.

// IntelligenceService: ограниченное ожидание и проверка ответа
const response = await fetch(`${serviceUrl}/interpret`, {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ totalClients, quartilesCount, segments }),
  signal: AbortSignal.timeout(4000),
});
if (!response.ok) throw new Error('AI service unavailable');

Алгоритм просмотра истории анализа

Цель: предоставить пользователю сохранённые ранее запуски и результаты анализа.

Шаги:

  1. Пользователь открывает историю анализов.
  2. Клиент запрашивает список через защищённый маршрут GET /api/rfm/analyses.
  3. Сервер использует идентификатор пользователя из проверенной JWT-cookie и выбирает только принадлежащие ему конфигурации анализа.
  4. При открытии записи клиент передаёт её идентификатор в запросе результатов.
  5. Сервер проверяет принадлежность конфигурации текущему пользователю и возвращает результаты или отказ в доступе.

Результат: пользователь просматривает собственные сохранённые анализы и их результаты.

4.3.8 Механизмы обеспечения информационной безопасности

В системе применяются меры защиты на уровне аутентификации, обработки запросов, хранения паролей и настройки HTTP-взаимодействия.

  • Пароли пользователей хранятся в виде bcrypt-хеша; открытое значение пароля не сохраняется.
  • Для аутентификации применяется JWT в cookie с флагом HttpOnly и настройкой SameSite Strict; клиентский JavaScript не получает токен и не сохраняет его в localStorage.
  • Защищённые маршруты backend требуют успешной проверки JWT. Для регистрации и входа предусмотрены ограничения частоты запросов.
  • ValidationPipe разрешает только объявленные DTO-поля и отклоняет неизвестные свойства; JSON-тело ограничено по размеру.
  • CORS ограничивает источник клиентского приложения и разрешает передачу учётных данных только для настроенного origin.
  • Устанавливаются заголовки защиты от MIME-sniffing, встраивания страницы во фрейм и передачи Referer; в production включается HSTS.
  • Пользовательские ошибки API обрабатываются общим фильтром, а диагностические сообщения запуска не выводят значения конфигурационных секретов.
  • Интеллектуальный сервис получает агрегированные сведения о сегментах, а не имена, контакты или записи транзакций.

Для рабочего развёртывания вне локальной среды необходимо использовать HTTPS на reverse proxy, задать production-режим и сильный секрет JWT. Ограничители частоты запросов хранят состояние в памяти процесса; при запуске нескольких экземпляров backend их следует заменить общим хранилищем, например Redis. Текущая схема общих таблиц клиентов и транзакций требует отдельного решения по изоляции данных организаций перед многопользовательским межорганизационным развёртыванием.

В разделе спроектировано и описано программное решение для автоматизированного RFM-анализа. Система включает React-клиент, серверное приложение NestJS, базу PostgreSQL и изолированный экспертный микросервис. Сервер обеспечивает детерминированный расчёт RFM-показателей, формирование сегментов и сохранение результатов вместе с параметрами анализа. Интеллектуальный компонент выполняет интерпретацию агрегированных данных и не влияет на числовой расчёт. Описаны программные интерфейсы, последовательность обработки данных и применяемые механизмы защиты.
