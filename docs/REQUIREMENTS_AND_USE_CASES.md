# Требования и пользовательские сценарии

Документ фиксирует функциональность, подтверждённую текущей реализацией, и задаёт критерии приёмки для дальнейшей разработки и курсовой записки. Он не утверждает, что система уже прошла ручную приёмку или испытания на промышленной нагрузке. Пользовательские данные в автоматизированных проверках заменены синтетическими.

## Пользователи и границы системы

Основная роль — зарегистрированный аналитик клиентской базы, который импортирует данные, выполняет RFM-анализ и изучает результаты. Незарегистрированный посетитель может создать учётную запись или войти. Отдельная административная роль и её функции в текущем приложении не заявлены.

В систему входят браузерный интерфейс, REST backend, PostgreSQL и отдельный сервис экспертной интерпретации. RFM-расчёт выполняет backend. Сервис интерпретации формирует текстовые наблюдения и рекомендации по агрегатам сегментов; он не обучает ML-модель и не заменяет проверку аналитиком исходных данных.

## Пользовательские сценарии

### UC-01. Вход в систему

**Основной участник:** зарегистрированный аналитик. **Предусловие:** учётная запись существует и активна.

1. Аналитик открывает форму входа и вводит email с паролем.
2. Интерфейс отправляет данные по HTTPS в production и принимает HttpOnly-cookie.
3. Интерфейс открывает рабочее пространство и загружает профиль.
4. При неверных данных показывается безопасная ошибка, защищённые данные не открываются.

**Результат:** аналитик авторизован либо остаётся на форме входа без доступа к данным.

### UC-02. Безопасный импорт клиентской базы

**Основной участник:** авторизованный аналитик. **Предусловие:** файл CSV/XLS/XLSX содержит обязательные поля; формат и пределы перечислены в `API_CONTRACTS.md`.

1. Аналитик открывает импорт и выбирает файл.
2. Система отправляет его на предпросмотр и проверяет заголовки, строки, суммы и даты без сохранения.
3. Интерфейс показывает сводку, пример и ошибки, если они есть.
4. Если проверка успешна, аналитик подтверждает запись.
5. Система атомарно добавляет клиентов аккаунта и их транзакции, затем показывает число сохранённых записей.

**Альтернативы:** файл повреждён, слишком велик, имеет неверные поля или содержит ошибочные строки — API возвращает ошибку, частичные данные не сохраняются.

### UC-03. Расчёт и исследование RFM

**Основной участник:** авторизованный аналитик. **Предусловие:** в аккаунте есть покупки в выбранном интервале.

1. Аналитик задаёт начальную и конечную даты и число квантилей.
2. Backend выбирает только транзакции владельца и вычисляет Recency, Frequency и Monetary для каждого клиента.
3. Backend назначает оценки и сегменты и сохраняет анализ с историей.
4. Backend запрашивает текстовую интерпретацию по агрегатам сегментов.
5. Интерфейс показывает итог, метрики, графики, фильтруемую таблицу и карточки клиентов.
6. Аналитик при необходимости экспортирует результат.

**Альтернативы:** период пустой или даты некорректны — анализ не создаётся; AI недоступен — числовой результат остаётся доступен, статус интерпретации объясняет ограничение.
